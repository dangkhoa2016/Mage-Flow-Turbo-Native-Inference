## 1. Purpose

The first public `v1.0.0` release will present a strict, reproducible native-inference comparison across two Mage-Flow-Turbo diffusion representations and two execution backends:

| Profile | CPU | NVIDIA T4 `cuda0` |
|---|---:|---:|
| `q8-reference` | required fresh qualification | required fresh qualification |
| `bf16-safetensors` | required fresh qualification | required fresh qualification |

Each cell uses the same canonical protocol and the same frozen release source. The release is not qualification-complete until all four cells have produced independently reviewable evidence.

The redesign supersedes the prior release contract in which Q8 was CPU/CUDA capable and BF16 was an opt-in CPU-only experimental profile. The repository name remains `Mage-Flow-Turbo-Native-Inference` because the project is a native inference/deployment stack, not a GGUF-only or Q8-only repository.

## 2. Release positioning

### 2.1 Runtime identity

All model execution remains native and goes through the pinned `stable-diffusion.cpp` `sd-cli` runtime.

- No Hugging Face Transformers inference loop is introduced.
- No PyTorch inference backend is introduced.
- Python remains orchestration, validation, CLI/REST, lifecycle, telemetry, and evidence collection.
- `SafeTensors` and `PyTorch/Transformers-style distribution` describe artifact format/source layout, not the execution framework.

### 2.2 Profile roles

`q8-reference` remains the canonical/default v1.0.0 profile.

`bf16-safetensors` becomes a fully supported alternative release profile for CPU and CUDA0 qualification. It is no longer named `bf16-high-memory-cpu`, because that name would contradict CUDA support.

The release must not claim that BF16 is universally higher quality than Q8. Historical visual evidence can remain as background, but the 2x2 qualification matrix measures reproducibility, feasibility, latency, memory/VRAM behavior, and artifact correctness under a common protocol.

## 4. Native runtime contract

The pinned upstream runtime commit remains:

`6b3edaaf32cc19e5bb2d819c788bd557eddc8eba`

The release uses prebuilt runtime binaries for qualification. Production qualification must not build `stable-diffusion.cpp` from source inside a Kaggle evidence session.

Runtime evidence records the pinned upstream commit, `sd-cli` binary SHA-256, version output, device-list output, resolved executable path, runtime backend, and CUDA visibility policy for GPU runs.

CPU and CUDA binaries may have different binary SHA-256 values, but each platform's expected runtime hash must be frozen in source before the final qualification sessions begin.

## 5. Canonical 2x2 benchmark protocol

### 5.1 Fresh-session isolation

Run four fresh Kaggle sessions:

1. Q8 / CPU
2. BF16 / CPU
3. Q8 / T4 CUDA0
4. BF16 / T4 CUDA0

A session may not contain both Mage-Flow diffusion families during ordinary qualification. Each session attaches only the selected diffusion family plus its required shared artifacts and the correct prebuilt runtime.

### 5.2 Canonical request

Every cell uses:

- Prompt: `A small red fox sitting in a quiet green forest, natural light, detailed photography.`
- Seed: `42`
- Steps: `4`
- CFG: `1.0`
- Threads: `4`
- Generation count: exactly `1` per resolution

### 5.3 Resolution matrix

Every cell attempts, in order:

1. `512x512`
2. `640x640`
3. `768x768`
4. `1024x1024`

The matrix is sequential. No two generations run concurrently in a qualification session.

### 5.4 Fail-fast behavior

A cell begins with 512x512. If setup or 512 fails, later resolutions do not run.

If a later resolution fails due to a real runtime condition such as CUDA OOM, host-memory headroom failure, unsupported tensor operation, or another reproducible runtime error, the matrix stops at that resolution and records the failure.

The release does not alter placement policy or silently fall back merely to make a cell pass.

## 6. Backend policy

### 6.1 CPU runs

CPU qualification requires:

- Kaggle `Accelerator=None`;
- no visible NVIDIA GPU;
- backend exactly `cpu`;
- prebuilt CPU `sd-cli`;
- no CUDA fallback or accelerator auto-selection;
- host memory telemetry;
- process RSS telemetry.

### 6.2 T4 runs

GPU qualification requires:

- Kaggle T4 or T4x2 session;
- every visible physical GPU before masking must be NVIDIA T4;
- `CUDA_DEVICE_ORDER=PCI_BUS_ID`;
- `CUDA_VISIBLE_DEVICES=0`;
- effective runtime device `cuda0`;
- `cuda1` not visible to the inference process;
- no multi-GPU split;
- no `auto-fit`;
- no CPU inference fallback;
- no backend substitution;
- positive GPU-memory telemetry for successful generations.

A T4x2 host is allowed only as a physical host configuration; release qualification still uses one physical T4, slot 0, as `cuda0`.

### 6.3 Parameter placement fairness

The release benchmark must use one explicit, documented placement policy per profile/backend combination.

The policy must not hide BF16 feasibility problems by introducing undocumented CPU offload. If BF16 on a single T4 requires a different parameter placement than Q8, that difference must be explicit in the frozen source contract, justified before qualification, recorded in evidence, shown in the benchmark report, and treated as part of the profile/backend definition rather than an invisible fallback.

The preferred first design is full `cuda0` execution/parameter placement for both GPU cells. If BF16 512 cannot run under that policy, the failure is reviewed before any release-contract change.

## 7. Profile contract redesign

The Kaggle profile registry changes from:

- `q8-reference`: CPU, CUDA0
- `bf16-high-memory-cpu`: CPU only

to:

- `q8-reference`: CPU, CUDA0
- `bf16-safetensors`: CPU, CUDA0

The BF16 minimum-RAM rule becomes backend-aware:

- CPU BF16 retains a minimum visible-host-RAM policy and minimum `MemAvailable` headroom gate.
- CUDA BF16 does not reuse the CPU-only 27 GiB rule as its primary feasibility gate. It still records host memory telemetry, but GPU success is governed by runtime success, exact CUDA placement, valid artifact production, and VRAM telemetry.
- No CPU fallback is allowed when CUDA BF16 fails.

The old profile name may be accepted only as a compatibility alias outside release qualification if doing so does not create ambiguity. Release evidence, docs, manifests, and asset names use only `bf16-safetensors`.

## 8. Qualification harness redesign

The existing matrix harness is generalized from CPU-only to explicit backend support.

Required behavior:

- accepts `--backend cpu|cuda0`;
- accepts `--profile q8-reference|bf16-safetensors`;
- resolves the correct prebuilt runtime for the backend;
- verifies runtime binary SHA-256 before inference;
- verifies model manifest before inference;
- records source HEAD and source TREE;
- records the exact profile/backend pair;
- uses the same resolution parser and ordered matrix;
- sets `collect_cuda=True` for CUDA0 runs and `False` for CPU;
- preserves CPU memory telemetry;
- records GPU peak MiB for CUDA runs;
- writes one per-resolution record plus one aggregate;
- stops on first failed resolution;
- never retries a launched canonical generation inside the same authority session.

A qualification record must contain enough information for an independent reviewer to verify the result without trusting terminal prose.

## 9. Evidence schema

Each per-resolution record includes:

- schema version;
- release version;
- source HEAD;
- source TREE;
- profile;
- backend;
- session identity;
- host/accelerator evidence;
- runtime identity and binary SHA;
- model component filenames, formats, quantizations, and SHA-256 values;
- canonical request fields;
- resolution;
- process exit state;
- elapsed milliseconds;
- host-memory metrics;
- peak `sd-cli` RSS;
- GPU peak MiB for CUDA;
- artifact filename, byte count, dimensions, and SHA-256;
- failure classification when not successful.

The aggregate includes the ordered requested resolutions, completed resolutions, failed resolution if any, setup timings, runtime/model identities, matrix status, and identities for the per-resolution records.

## 10. Combined 2x2 comparison report

A deterministic offline comparator consumes the four independently reviewed matrix aggregates.

It first verifies comparability:

- same release source HEAD and TREE;
- same pinned upstream runtime commit;
- same canonical prompt, seed, steps, CFG, and threads;
- same ordered resolution list;
- same Qwen identity;
- expected profile-specific diffusion identities;
- expected VAE identities;
- CPU cells actually use CPU;
- T4 cells actually use CUDA0 slot 0;
- no mixed-family input;
- no silent fallback.

Only after comparability passes may it compute ratios.

For each resolution where both relevant cells succeeded, report Q8 CPU→T4 speedup, BF16 CPU→T4 speedup, CPU Q8↔BF16 latency and RSS comparison, and T4 Q8↔BF16 latency and VRAM comparison.

If one cell failed at a resolution, the report shows the failure classification and does not invent a performance ratio for that comparison.

## 11. Acceptance semantics

### 11.1 Qualification execution result

A cell can be:

- `PASS`: all required resolutions completed successfully under policy;
- `PARTIAL_WITH_RECORDED_LIMIT`: 512 passed but a later resolution hit a genuine, independently verified platform/runtime limit;
- `FAIL`: setup, canonical 512, identity, policy, evidence, or integrity gate failed.

### 11.2 Release decision

A `PARTIAL_WITH_RECORDED_LIMIT` is not silently treated as `PASS`.

Whether v1.0.0 may publish with such a result is a separate release-decision gate after independent review. The release notes must state the limitation prominently if accepted.

Identity mismatch, fallback, mixed-family contamination, evidence corruption, source mismatch, or policy violation is never an acceptable recorded limit; those are hard failures requiring correction and a fresh run.

## 18. Non-goals for v1.0.0

The strict 2x2 redesign does not add multi-GPU qualification, `cuda0&cuda1` release placement, P100 qualification, TPU support, Vulkan/Metal/ROCm/SYCL release qualification, Hugging Face Transformers inference, PyTorch inference, model training or fine-tuning, automatic model-family conversion, visual-quality superiority claims from the performance matrix, or any public release version before the first `v1.0.0`.

## 19. Success criteria

The redesign is implementation-complete when source exposes the two approved profiles; both profiles support CPU and CUDA0 according to explicit policies; the matrix harness/evidence schema supports all four cells; the comparator produces a strict comparability-gated 2x2 report; docs and provenance accurately describe the architecture; full tests/audits pass; public history is coherent and uses the required author identity; and a new exact release HEAD/TREE is frozen.

The first public `v1.0.0` is publication-ready only after the four fresh qualification cells, independent artifact reviews, combined report review, and final publication audit complete under that new frozen source authority.
